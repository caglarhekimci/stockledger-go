# StockLedger — design

Date: 2026-11-03. User delegated product and architecture choices and authorized implementation, testing and GitHub push.

## Intent
An independently runnable inventory reservation service demonstrating the database, concurrency, API, asynchronous processing and operability skills seen in Türkiye Go postings.

## Architecture
A Go modular service with ports and adapters: domain has reservation invariants; application consumes small repository interfaces; PostgreSQL owns transactions, stock and idempotency; HTTP adapts authenticated requests. Redis provides tenant-scoped rate limiting. Kafka receives durable transactional outbox events from a separate worker process. Composition is in cmd/stockledger. No domain dependency on HTTP, Redis or Kafka.

## Product behavior
Tenant-scoped API keys configured by environment. Create/list stock items; reserve stock atomically with caller-provided Idempotency-Key; confirm or release reservations with legal state transitions. Reject mismatched idempotent payloads and prevent negative stock under concurrent requests. A PostgreSQL transaction writes the stock mutation, reservation and outbox together. Worker publishes with stable event IDs and at-least-once semantics, acknowledges only after success; consumer deduplication is documented. Reads are never served from Redis to preserve stock correctness.

## Constraints
Use official supported Go toolchain; PostgreSQL, Redis, Kafka adapters must be real. Docker Compose local stack and GitHub Actions service integration tests. Unit tests, real PostgreSQL integration tests, HTTP security/validation tests, race tests on Linux, go vet and govulncheck. No fabricated performance or production-readiness claims. No external cloud provisioning or paid service. Secrets never committed.

## Choices
Chosen: cohesive domain plus separate API/worker process. Alternative: many independent microservices incurs distributed transaction and operations overhead without a matching domain need. Alternative: in-memory CRUD does not demonstrate durable transaction integrity. gRPC and Kubernetes are documented future tradeoffs, not claimed implementations.

## Quality / acceptance
Small consumer-owned interfaces; explicit error mapping; context cancellation and timeouts; graceful shutdown; structured logs; health/readiness; Prometheus metrics. OpenAPI, ADRs, sequence/ER diagrams, threat model and runbook. Tests must verify tenant isolation, concurrent oversell prevention, idempotency conflict/replay, state transitions and outbox retry. Docker CI must exercise real services. README English, research Turkish.
